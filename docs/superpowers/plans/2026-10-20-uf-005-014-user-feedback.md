# UF-005–UF-014 User Feedback Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> Execution method for this delivery: **native** (the user's brief mandates autonomous implementation with independent work continuing; only UF-010 product rules are an allowed user question). Plan is saved for review; the user may inspect it at any time.

**Goal:** Implement user feedback UF-005…UF-014 in the 代肝记录 Android app while preserving the v1.6 fixes (UF-001…UF-004).

**Architecture:** Room (schema 8 → 9) with repositories as single write gateways inside `database.withDatasetTransaction`; Compose UI per feature package; strict backup catalog (`BackupTableCatalog`) that must list every new table/column. New capability is additive: nullable columns and new tables only; historical data and v1.6 behaviors are untouched.

**Tech Stack:** Kotlin, Jetpack Compose (Material3), Room + Hilt, JUnit4 instrumented tests (Android SDK 36.1 emulator) + JVM unit tests.

**Spec:** `docs/user-feedback-issues.md` (UF-005…UF-014 sections), `docs/handoffs/v1.6-user-feedback.md` (regression baseline), `docs/data-model.md`.

## Global Constraints

- Preserve v1.6 behavior: date correction (updateOrderDates rules), 误建订单删除/作废 rules, archived-account folding, MONTHLY/monthDay recurrence, renewal semantics. Existing tests must stay green.
- Chinese UI wording consistent with the app (现有风格：短句、明确后果提示、确认框说明不可撤销).
- Money is integer cents (`Money.MAX_CENTS` = 9 999 999.99 元); timestamps epoch millis; dates ISO `yyyy-MM-dd`.
- All destructive/multi-row writes run in one Room transaction (`withDatasetTransaction`). Attachment **files** are deleted after DB commit; failures are recovered by `AttachmentRepository.cleanupOrphans()` (called at app start and after deletions).
- Backup format: `BackupTableCatalog` is a closed catalog; any new table/column must be added there, in `BackupValidator`, `BackupDataCodec`, and old backups must restore (new columns default NULL / new tables empty). Template exchange (`TemplateFileCodec`) must round-trip changed template fields.
- Schema history 1–8 stays read-only; only `MIGRATION_8_9` and `RecordDatabase/9.json` are added.
- No publishing, no push, no release unless separately requested. APK builds keep the project's debug signing.

## Review Focus

1. **Cascade deletes leave foreign-key orphans** (receipt corrections, completion batch items, creation operations referencing deleted rows) → Tasks 4–5 tests assert every referencing table is empty after delete and `PRAGMA foreign_key_check` is clean.
2. **Price edit rewrites or drops receipts / breaks paid≤price math** (previously a hard invariant) → Task 3 must keep receipt rows byte-identical and make `Balances`/`ReceiptLedger` tolerate paid > price instead of throwing (`Money.remainingCents` currently throws; that throw is a crash path).
3. **Weekly-task history LazyColumn key collision** (two occurrence rows of one task sharing a clamped `gameDate`) → Task 7 reproduces exactly this data shape via the public backfill API and scrolls the detail list to the bottom.
4. **Old backup (v1.6 schema 8 catalog) restore into schema 9** silently rejects or drops data → Task 1 compatibility test restores a schema-8-shaped backup and asserts NULL/empty defaults for the new fields.
5. **Server options leak across games or rewrite account.server on option rename** → Task 2 tests assert per-game isolation and that editing/deleting options never touches `game_accounts.server`.

### Task 7: UF-014 hosting-detail scroll crash

**Root cause (evidence-based):** For weekly tasks the occurrence key uses the **unclamped** window start (`W:<start>`) while `gameDate` stores the **clamped** display start (`OccurrenceRules.weeklySlot`, `ensureOccurrence`). When a hosting period begins on a game day that straddles the weekly-refresh moment, two windows touched by that game day both clamp to `period.startDate`; the backfill API (`setHistoricalCompletion` with explicit `weeklyWindowStart`, exposed in 补录/更正 UI via `slotsForDate`) can create occurrence rows for BOTH windows. `OrderDetail.historyEntries()` then yields two entries with the same `(taskId, attributedDate)`, and `OrderDetailScreen` builds LazyColumn keys `"history-${taskId}-${attributedDate}"` — **duplicate keys throw `IllegalArgumentException: Key … was already used` when the lazy key index map covers them while scrolling toward 本期打卡记录/往期记录/收款 at the bottom**.

**Files:**
- Modify: `feature/orders/OrderDetailScreen.kt` (keys), test only elsewhere unless a second defect reproduces
- Test: `androidTest/.../ui/OrderDetailScrollCrashTest.kt` (new)

- [ ] **Step 1: Failing reproduction test** `OrderDetailScrollCrashTest`: create hosting order whose `startDate` is the weekly-boundary game day (weekly refresh mid-day), weekly + daily tasks, backfill both touched windows for the boundary day via `setHistoricalCompletion` (two explicit `weeklyWindowStart` values), add receipts (incl. one REPLACED chain) and attachment rows; open `OrderDetailScreen`; scroll to `order-detail-payment-section`; assert composable still displayed (no crash). Also cover a 3-period renewal history combo.
- [ ] **Step 2: Run → FAIL (crash).** Capture logcat stack as evidence.
- [ ] **Step 3: Fix** keys to `"history-${entry.occurrenceId}-${entry.taskId}-${entry.attributedDate}"` (occurrenceId null → task-only path) — occurrence ids are unique per row, so legacy/odd data cannot collide. Re-run test → PASS.
- [ ] **Step 4: Regression** — `OrderDetailScreenTest`, `OrderDetailConsistencyTest`, `CancelledReceiptUiTest` stay green. Commit `fix: unique lazy keys for hosting history to stop bottom-scroll crash`.
